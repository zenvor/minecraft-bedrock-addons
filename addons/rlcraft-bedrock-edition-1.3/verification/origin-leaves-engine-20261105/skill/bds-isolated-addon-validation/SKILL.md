# BDS 隔离附加包验证

先明确被测行为、修复前输入和成功条件。静态检查、启动、原生 API、完整整合包和玩家验收是不同层次，报告实际验证范围。

## 输入与保护边界

- 检查仓库规则、HEAD、工作区差异及候选包，保留无关改动。确认打包器读取工作区还是 Git ref，避免遗漏未提交修复。采用基线归档加精确覆盖清单时，核对其余文件字节、UUID、版本、依赖和 ZIP 内容，记录包与逐文件 SHA256。
- 只读发现正式及备份服务、当前 PID、引擎哈希、世界及包目录，保存关键配置、包顺序和用户要求保留文件的哈希。不要沿用历史 PID。测试不需要重启正式服务或操作备份。
- 建立唯一 owner/run_id 的 `/var/tmp/bds-addon-probe-*` 目录和独立 unit。新建一次性世界，不复制正式世界或备份。运行文件按白名单准备，不复制 backups、addon-archive 或其他暂存目录。

## 隔离与资源

Linux/systemd 配置与脚本协议见 [运行协议](references/runtime.md)。使用私有网络命名空间、测试端口、独立目录；在测试 mount namespace 内把正式目录只读。限制 CPU、内存、swap、运行时间和进程数，不修改正式 unit。

预算包括启动器、监控器和缓存。准备完成即退出准备进程，再启动单个测试实例；资源不足时延期或报告受限。只读共享经哈希确认一致的引擎、vanilla 和未改依赖包能减少重复缓存，不能用可写硬链接。低 MemoryHigh 可让 MC_SERVER 卡在内存回收路径，不能称为模组死锁；功能验证采用合适的硬限额，记录 memory.events/pressure。

[runner.py](scripts/runner.py) 和 [guard.py](scripts/guard.py) 是已运行的监控组件，须配合案例配置和探针，并非完整安装器。guard 只有同时匹配 PID、exe、cwd、netns、cgroup，且 PID 不在保护列表时，才终止测试进程。正式服与测试可共享同一 exe，不能据此识别进程。

## 对照验证

先做正向对照证明夹具有效，再顺序运行修复前和修复后输入。主动触发全部目标，检查原生返回及实际世界状态；安静启动不证明惰性解析错误消失。

对于 structure_template_feature 白名单，保留原 JSON 字节、路径和 identifier，用真实依赖包的方块。通过 feature_rules 引用 feature 使其进入 registry；规则可匹配不存在的 biome tag，避免自然生成，再显式调用原生 API。用小结构夹具时，只改测试包内的结构输入，先检查大小与内容，明确未验证原完整结构或整合包。实例见 [origin_leaves 案例](references/origin-leaves-case.md)。

核对目标覆盖、基线错误复现、修复后目标计数、所有未预期 ERROR、Watchdog、OOM、资源保护动作和保护进程状态。区分预期基线错误与新脚本异常。

运行前选择退出方式。正常保存/关服验证需要对应退出证据；一次性功能测试可在 complete 后计划 SIGTERM，保留 marker 和退出码，但不能声称验证正常关服。资源保护终止、超时、OOM、fatal 或未完成均不算成功。

## 归档与清理

保留包哈希、清单、探针、完整 BDS 日志、逐项结果、unit 参数、netns/cgroup、资源采样及失败尝试。再次核对正式服务/PID 和保护资产。

先下载并校验证据，再确认测试 PID 已退出、cgroup 无进程。只停止/卸载 owner 清单的准确 unit，并删除准确暂存目录；检查 unit、目录和测试进程无残留。不能按宽泛名称清理其他测试、备份或其他对话文件。保留源码、验证日志和测试包。

报告对照结果、验证与未验证范围、保护资产状态、包/报告路径及清理结果。隔离测试授权不等于部署、提交或推送授权。
